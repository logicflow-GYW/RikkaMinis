# 设计哲学：不只是「能做什么」，而是「如何决策」

RikkaMinis 的开发不是按需求清单推进的，而是由一套持续迭代的方法论驱动。这份文档记录的是**决策层的思维框架**——换一个开发者接手时，这些原则可以帮他理解「为什么这里选 A 不选 B」，而不必从代码反推设计意图。

---

## 一、验证优先于能力

> 「我不在乎模型傻不傻，我在乎输出能不能被验证。」

这是 RikkaMinis 最底层的价值取向。

传统的 AI 产品追求「模型更强」「回答更好」——能力的提升是无止境的，而且用户无法区分「真的好」和「看起来好」。RikkaMinis 的回应是**不赌能力，赌验证**。

具体做法：

- 任何方案提出时，优先回答「怎么验证」而非「效果多好」。
- 能设计成 A/B 测试的就设计成 A/B 测试（如语义记忆 vs 关键词 grep）。
- 外部机制（CI、真机测试、日志 grep）优先于内部判断（模型自评正确性）。

验证需要 ground truth。一个好的测试框架（harness）可以放大能力，但不能替代能力（地板效应）——能力不足时测再多也不会对，但能力足够时 harness 让你知道它**确实**对了。

---

## 二、种子方法论：面对新能力时的正反馈循环

面对一个不熟悉的新能力（新平台、新 API、新工具）时，不要从「它能做什么」出发，而是从一个**具体种子**出发。

过程只有四步：

```
1. 找「真正做不到」的点
   → 这个能力让 agent 能做什么 shell 做不到的事？
   → 不是「更好/更快/更方便」，是「没有它就不成立」

2. 找对比
   → 设计一个 A/B 测试：不用这个能力 vs 用它，结果放在一起看
   → 对比本身就是 proof，不需要长篇论证

3. 做成种子，不是系统
   → 10 分钟内能跑通的最小原型，不是架构设计
   → 目标：到达「用户亲眼看到价值」的那一刻

4. 用户看到结果，再决定固化
   → 用户说「有用」→ 固化为可复用脚本 + Skill
   → 用户没感觉 → 砍掉，不追加投入
```

这个方法论的核心不是「做出好东西」，是**在最短时间内到达用户亲眼看到价值的那一刻**——到达了就固化，没到达就换一个种子。比「做对」更重要的是「做快」。

实际案例：语义记忆系统（HF Dataset + embeddings）从一个 200 行 Python 原型起步，一次搜索的 A/B 对比（关键词 0 命中 vs 语义 3 条精准命中）就完成了验证，随后固化。

## 三、决策框架：加能力之前先问边界

> 「这个工具让 agent 能做什么之前做不到的事？如果答案是『能用 shell 做同样的事』，就不该加。」

这是一条硬约束：

- `shell_execute + android-* CLI` 几乎覆盖了 RikkaMinis 运行时的所有能力边界。
- 真正的瓶颈不是工具数量，是 agent 的智能性（规划、理解、纠错）。
- 每加一个新工具，增加了维护成本 + 复杂度 + 出错面，但能力增量却可能为零。

因此，面对任何「要不要加功能」的提议，先过这道门：

```
shell_execute 能做吗？  →  能  →  不加（最多封装成 Skill）
                       →  不能 →  继续问：这个不能是不是核心场景必需的？
                                →  是 →  加
                                →  不是 →  不加
```

这条原则避免了一个典型陷阱：把 RikkaMinis 变成一个臃肿的瑞士军刀，每把刀都不够锋利。

同样适用于模型选择、技能设计、UI 组件等任何层面的「加法决策」。

## 四、三平台的定位：不是越多越好，各司其职

RikkaMinis 选了三个外挂平台：GitHub、Cloudflare、HuggingFace。选它们不是图「多」，而是每个解决一个 shell 做不到的硬需求：

| 平台 | 解决什么 | 为什么 shell 做不到 |
|---|---|---|
| **GitHub** | 代码存储、CI 编译、发布 APK | 需要持久仓库 + 云端构建环境 + 版本分发，shell 只能 curl API |
| **Cloudflare** | 公网入口、边缘计算 | 设备在 NAT 后，无法对外暴露 HTTP 服务；CF Workers 提供零运维公网端点 |
| **HuggingFace** | 语义记忆跨设备持久化 | 关键词 grep 找不准（不同词表达同件事），需要 embeddings 做语义搜索 |

三者构成「一端脑、三平台手」的架构——不是任意三个平台凑数，而是各有一个 shell 无法替代的硬角色。

## 五、实战纪律（来自真实踩坑）

以下是开发过程中反复验证过的操作纪律，写入这里不是为了警示，而是为了让接手者不必重新踩一遍：

### 5.1 GitHub 操作一律走 gh_sync.sh

- 推送、触发 CI、查 CI、PR、issue、label、release 全部封装在 `skills/github-ops/scripts/gh_sync.sh`
- 禁止裸 `git remote set-url` 内嵌 token 或裸 curl
- 原因：`askpass` 机制保证 token 不落盘，且是标准流程

### 5.2 加字段「四处同步」+ round-trip 测试

- 数据类加字段必须同步：模型 → entity → toSnapshot → toProviderConfig
- 缺任何一层导致字段静默蒸发（存了但下次读不回来）
- 最好补一个 round-trip 测试（内存 set → save → 读回，字段不丢）

### 5.3 滚动问题排查顺序

- 先查持久化字段覆盖（跨层 gap），再查点击/重组
- 跨层数据丢失最容易伪装成「交互无反应」的 bug

### 5.4 自动跟随排查法

- 凡 `messages.size` 变化的 LaunchedEffect/collect，都要怀疑是否无条件 scrollToItem
- reverseLayout 高频插入时，视口 `firstIdx=0 但 firstOff≠0` 也是跳的信号

### 5.5 CI workflow 安全

- 任何发布步骤必须有 `if: github.ref == 'refs/heads/main'` 门控
- 否则 `workflow_dispatch` 分支构建会污染 release 资产

## 六、观测层原则（2026-09 新增）

观测层（诊断埋点、审计脚本、日志治理）是 RikkaMinis 最特殊的一层：应用的
**执行体与测量仪器是同一个东西**。下列原则全部来自这一层的真实翻车与修复，
配套设计档见 `docs/stability/observability.md`。

### 6.1 尺子也会接错线

census 曾把 7 个测量点接在一个"长得像活代码"的 legacy 渲染器上（实际只服务
已废弃的 flat 行管道），连续两天读数全 0，被误判为"这条路径没跑"。接线时
必须追问：**"这个函数在目标配置下真的会被执行吗"**——而不是"它长得活不活"。
修正语义：一个测量点必须接在"预期会跑"的路径上，此时 0 才是异常。

### 6.2 让沉默可区分

死掉的测量点不会报错，它只会安静地不被触发。对策不是"加更多日志"，而是让
尺子**无法保持沉默**：首见必报（first-hit 行）+ 窗口汇总携带未触发分支的
0 值——"没触发"本身变成一次测量。

### 6.3 一个接线点 = 一个语义

一个分支名只允许有一个接线位置。同名多调用点是双向陷阱：既能让死探针在
审计里隐形（另一个调用点还活着），也能让有意的单点门控被误报为批量删除。

### 6.4 审计粒度要对齐

"某 tag 是否活着"与"某行是否活着"是两个粒度，结论可能相反。动"批量统计"
类审计前先想清楚：测的是行的存亡还是 tag 的存亡。

### 6.5 观测设施自身要可审计

死尺子的反面是登记册（RARE）**有保质期**：登记项在新构建里复活或死透时，
条目必须更新，否则它从"已知例外"腐化为"永久盲区"。`scripts/diag/
liveness_audit.py` 的 pending-install 机制（装包前静默、首见命中即提示
prune）就是为此。观测层的信任不来自"我们记得"，来自"它会自己报告过期"。

## 七、这些原则之间的关系

```
验证优先（一）
    ↓ 决定怎么判断一个东西值不值得做
种子方法论（二）
    ↓ 决定面对新能力时用什么节奏验证
决策框架（三）
    ↓ 决定什么该加、什么不该加
三平台定位（四）→ 实战纪律（五）→ 观测层原则（六）
    ↓                   ↓                   ↓
  架构边界            操作安全网          测量可信度
```

这不是一份「应该遵守」的规范，而是一份**已经通过实战验证**的决策记录。如果未来的场景和这些原则冲突，以场景为准——但至少知道当初为什么这样选。
