**这改变什么用户行为？**

- **B2**：用户在编辑 A 消息的状态下、未退出编辑就长按编辑 B 并发送 → B 的消息体里**不再出现**自己没发出去的草稿粘贴块。
- **B3**：系统分享一个已失效附件 / 纯空白文本 → 输入框不再被「武装」，「移动到…」胶囊**不会**在之后随手输入的无关草稿上冒出来；正常文本分享与正常附件分享的胶囊行为**完全不变**。

两条都属于「用户可见内容被污染 / 无关 UI 反向复活」，不是纯内部整理。

## 3 修法（阶梯第 6 级：最小实现，各一条判据）

**B2** — 把「进入编辑态时 paste 行怎么变」抽成纯函数，调用点只套用：

```kotlin
internal data class EditPastesEntry(val snapshot: List<PastedText>, val live: List<PastedText>)

internal fun editPastesOnEnter(current: List<PastedText>, snapshot: List<PastedText>?): EditPastesEntry =
    EditPastesEntry(snapshot = snapshot ?: current.toList(), live = emptyList())
```

`editMessage()` 里原来 7 行的手写分支换成 3 行（`_preEditPastes.value = entry.snapshot` / `_pastedTexts.value = entry.live`）。语义：**进入编辑态（首次或重入）恒为「快照一次 + 活跃行清空」**，只有 `cancelEdit()` 把快照还回来。`_preEditAttachments` 的既有语义、`cancelEdit()` 还原、`stashPastedText` / `expandPastedTextWithSplit` / `sendMessage` **一行未动**。

同一条消息重入：快照保持原样，活跃行清空后由下方 refold 重新 stash 一次 → 仍然只有一个 chip。

**B3** — 落点判据抽成纯函数，`ChatScreen` 的 drain 循环记录真正落地的项：

```kotlin
internal fun shareDrainLanded(
    items: List<PendingShare.Item>,
    attachmentLanded: (PendingShare.Item) -> Boolean,
): Boolean = items.any { item -> when (item.kind) {
    INLINE_TEXT -> item.value.isNotBlank()
    ATTACHMENT  -> attachmentLanded(item)
} }
```

- 附件分支改为 `if (viewModel.addAttachmentFromStagedShare(...) != null) landed += item`（以返回值为准，不以意图为准）。
- `markShareInjected()` 只在 `shareDrainLanded(pending.items, landed::contains)` 为真时调用；一项都没落地则**既不武装也不 disarm**（保持上一次的状态语义），并留一条 `[Share] N item(s) landed nothing; capsule not armed` 日志。
- **未修改** `MoveToCapsuleGate` 判据本体（`canMove` / `shouldShow` / `observeFrame` 逐字未动），B1 的几何问题不在本支。

> 说明：`shareDrainLanded` 放在 `ChatViewModel.kt`（该文件末尾本就是顶层 pure 辅助的家，如 `pruneExpiredShareInboundFiles` / `SHARE_INBOUND_TTL_MS`），而不是 `MoveToCapsuleGate.kt` —— 避免动「判据本体」文件，同时让 JVM 测试能直接驱动。

## 6 残留（带触发条件 + 触发后方案）

1. **编辑态内手动新粘贴的块在重入另一条消息时丢失**（非本支引入的「新」缺陷，是清空语义的边界）：用户在编辑 A 时自己再粘一段长文本形成 chip，然后直接编辑 B → 该 chip 既不在快照也不在活跃行。触发条件：真机上有人这样操作并报告内容丢失。触发后方案：把「进入编辑态时的活跃行」与「快照」分开记账（新增第三槽 `_editSessionPastes`），或在 `onEdit` 入口在编辑态时先 `cancelEdit()` 再进入——**需真机证据再动**（当前无任何报告），登记于 backlog §INCR-1117B。
2. **纯空白分享仍会向 composer 追加空白文本**（`AppendText("   \n")`），只是不再武装。影响：输入框可能多出空行。触发条件：用户反馈「分享后输入框莫名多空行」。触发后方案：在 drain 的 `INLINE_TEXT` 分支前置 `item.value.isNotBlank()` 守卫（一行，与 `shareDrainLanded` 同一判据）。
3. **`clearChat()` 不清 `_pastedTexts`**（既有行为，本支未改）：清空会话后活跃 paste chips 仍是旧的。触发条件：清空会话后 chip 仍在且可发送。触发后方案：在 `_preEditPastes.value = null` 旁补 `_pastedTexts.value = emptyList()`（需先确认 `clearComposerInput` 是否已覆盖）。

## 7 未验证边界（真机清单）

1. 编辑 A（A 含长粘贴）→ 不退出直接编辑 B（B 含长粘贴）→ 发送：B 消息体只含 B 自己的粘贴 + 编辑后的提示词，**不含**草稿内容；chip 行只有 1 个。
2. 同上，在 B 编辑态点「退出编辑」：输入框恢复为**进入编辑前的草稿**（含草稿 chip 与标题），A 的 chip 不残留。
3. 纯文本分享（如浏览器"分享链接"）：胶囊照常出现，移动后目标会话内容完整。
4. 分享一个已损坏/已删除的图片文件：胶囊**不出现**，之后随手输入文字胶囊也不出现。
5. 同一消息重复进入编辑（A → 退出 → A）：chip 数不翻倍。
