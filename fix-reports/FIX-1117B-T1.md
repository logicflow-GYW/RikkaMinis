## 2. 修法

### 2.1 `SubagentDispatchPin`：把「计数 + Room 往返」做成一个互斥窗口操作

```kotlin
suspend fun beginWindow(sessionId, readPinnedAt, pin): Int =
    withContext(NonCancellable) { lockFor(sessionId).withLock { depth++; if (depth==1 && read==null) pin+record } }

suspend fun finishWindow(sessionId, readPinnedAt, unpin): Boolean =
    withContext(NonCancellable) { lockFor(sessionId).withLock { depth--; if (last) { read==ours → unpin; 记账后清除 } } }
```

- **A3-a**：`end()` 与随后的两次 Room 调用被同一把 per-session `Mutex` 覆盖 ⇒「窗口已关且 `pinned_at` 已还原」是一个原子步，新窗口只能观察到「不是在还原中」的状态。不变量一句话：**开窗/关窗之间不存在可被另一窗口观察的中间态**。
- **A3-b**：整个开窗动作在 `NonCancellable` 里，写库与记账不可被取消切开；且**开窗路径不再 catch 任何异常**——写库失败就没有记录（也就没有要还原的东西），不再有 `runCatching` 吞 `CancellationException` 的位置。
- `begin` / `end` / `noteWrittenPin` / `takeWrittenPin` 改为 `private`：调用点**无法**绕过锁（这是把竞态变成不可表达，而不是靠约定）。
- 还原失败（读/写抛异常）返回 `false` 且**保留记录**（下一个窗口可自愈），调用点 `AppLogger.warning` 记一条，不再静默。
- `windowLocks` 不随 `clear()` 重置（已在 KDoc 写明理由：等在锁上的协程会与新窗口拿到两把不同的锁）。

### 2.2 调用点变薄

```kotlin
SubagentDispatchPin.beginWindow(activeSessionId, { chatRepository.getSession(it)?.pinnedAt }, { chatRepository.pinSession(it, true) })
val result = try { … } finally {
```

### 2.4 CI 抓到的**门 ROT**：`subagent_dispatch_check.py` 的 D5 重锚（只改了这一个门）

**ROT 现象**（run `#3208 / 44013405495`）：
```
━━━ [31/115] Sub-agent dispatch guard ━━━
FAIL [dispatch-pin-missing]: the dispatcher must be pinned BEFORE the child runs
FAIL [dispatch-unpin-missing]: the pin taken for the dispatch must be released
```
**ROT 原因**：D5 只锚**调用点文本** `SubagentDispatchPin.begin(` / `.end(` —— 锚的是 token，不是决策。把记账搬进对象后，这两个 token 在原处消失（判据失明地报红）；反过来更糟：任何保留 token、丢掉「序列化 / 不可取消 / 只最后一个窗口还原」这些性质的调用点，会**继续绿**。所以是「判据锚点错了」，不是修法错（逻辑本身已被行为测试覆盖）。

**改门三件齐**：

1. **断言改锚到新决策**（并加负向断言）
   - D5（调用点）：pin 仍在子会话之前、unpin 仍在 `finally` 内；**新增负向** —— 调用点出现 `noteWrittenPin` / `takeWrittenPin` 即红（`dispatch-pin-bypasses-window`），因为那正是「两条挂起 Room 调用在窗口之外」的形态。
   - D5b（**新增，读 `data/SubagentDispatchPin.kt`**）：两个窗口操作都必须 ①`withContext(NonCancellable)` ②持 `withLock`；开窗 ③只在 `depth == 1` 时 pin（`pin-open-every-window`）④pin 前必须读当前值并与 `null` 比较（`pin-open-adopts-existing`）；关窗 ⑤undo 之前必须有「剩余深度」守卫（`pin-close-restores-early`）⑥undo 前必须读当前值（`pin-close-undone-blindly`）。
   - 深度守卫按**语义**判：先解析 `depths.merge/compute` 赋给的变量名，再要求该变量出现在某个 `if (...)` 条件里 —— `if (left != 0)` / `if (left > 0)` 或改写形态都不会失明。
2. **夹具同步**：`GOOD` 改成「委托式调用点」+ 新增 `GOOD_PIN`（对象）；`DIRTY` **9 → 20 臂**（12 条调用点 + 8 条对象）。每条臂现在断言**红的是哪一条 code**（旧版只要求「红」—— 夹具互相遮蔽时报不出是哪个判据死了）。
3. **`--selftest` 与真树都跑**：`SELFTEST OK (20 arms)`（20/20 各自红在自己的 needle 上，`GOOD`/`GOOD_PIN` 全绿）；真树 `OK: sub-agent dispatch wiring holds (5 call-site contracts + 8 pin-window decisions)`；另有 4 条**真树变异**证牙（§3.2 表下半）。

**没有改的**：`scan.sh` / `scripts/scan/scan_blocks.sh`（调用方式不变）、`test_scan.py`（它只断言本门输出含 `SELFTEST OK`，字形未变）、其它任何门。

**残留（P3，注释漂移）**：`scripts/scan/scan_blocks.sh` 第 31 块的注释仍写「parent pinned and released in a finally」，没提窗口操作与 D5b；本支未碰该文件，不影响判据。

## 4. 残留（如实登记，不修）

1. **还原失败路径无测试**：`finishWindow` 返回 `false` 的两个 `catch`（读/写抛异常）只有代码，没有用例。写它需要一个会抛的 fake —— 顺路成本 > 0，登记为 P3（若将来该路径出现在日志里再补）。
2. **失败后不重试**：还原失败时记录保留，但只有「同一会话的下一次派发」会用它自愈；若用户此后不再派发，pin 会留到用户手动取消。这是刻意的（后台重试需要调度器，收益不抵装置）。
3. **`windowLocks` 不回收**：每个派发过的会话一条 `Mutex`，进程级生命周期，与既有 `depths` 同量级。
4. **先证用的转写件不入仓**：`LegacyPinWindow` 在 `shared/work/incr1117b/t1probe/`（scratch），仓库里只有修复后的行为测试。仓库内无法在修复前编译「调用新版 API 的测试」，所以红是在转写件上取的。
5. 报告末条：`AppLogger.warning` 的文案没有断言（形状测试只断言 `if (!restored)` 存在）。
